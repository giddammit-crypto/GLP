## Итерация 24: ветка тачанок отделена от броневиков в древе пехоты

**Претензия.** «Ветка тачанок не должна соединяться (продолжаться) от ветки
броневиков… в идеале размести её под броневиками, чуть спусти ниже Спец
войска, чтобы они не накладывались друг на друга».

**Причина.** Все четыре технологии тачанок наследуют gridbox
`tech_trucks_tree` (якорь — `tech_trucks`; origin 140×620, слот 70 px,
формат `LEFT`: `x` — строка вниз, `y` — столбец вправо). Ванильные
броневики занимают ту же строку `x = 4` (пиксельная строка 900): стоя на
одной строке справа от `armored_car3`, ветка читалась как продолжение
броневиков, хотя никакого `path` между цепочками нет и никогда не было.

**Что сделано.**

1. `common/technologies/GLP_technologies.txt` — ветка переставлена на строку
   `x = 16` (пиксельная строка 1740) и в столбцы `y = 2/5/8/11` (280/490/700/
   910 px, шаг 3 слота = 210 px). Строка 16 — первая свободная ниже всего
   блока «Специальные войска» (заголовок 950..1012, морская пехота 1035,
   парашютисты 1165, горные стрелки 1275, рейнджеры 1405, спецназ
   1490..1630 px, последняя занятая строка — 1700), поэтому ветка:
   * не стоит на строке броневиков (`x = 4` / 900 px) и не читается как их
     продолжение;
   * не задевает ни одну цепочку спецвойск;
   * остаётся в видимой части древа (фон — 1400 px), прокрутки вправо не
     требует.
2. `common/technologies/zzz_GLP_tachanka_anchor.txt` — комментарий с
   раскладкой приведён к реальным координатам 1.19 (старый текст про «сдвиг
   броневиков вправо в 1.19» был неверен: они по-прежнему на столбцах
   1/8/12, то есть 210/700/980 px).
3. `tools/tech_tree_layout.py` — новый инструмент: локальная схема всего
   `infantry_folder` в реальных пикселях (gridbox'ы из
   `interface/countrytechtreeview.gui`, позиции технологий из
   `common/technologies/infantry.txt`). Ветку тачанок можно перетащить
   мышью, увидеть строки/столбцы, предупреждения о наложениях и сохранить
   результат прямо в файл технологий; после сохранения запускается
   `tools/glp_audit.py`.

**Проверка.** `python3 tools/glp_audit.py` → 0 ошибок, 0 предупреждений;
`collisions()` из `tools/tech_tree_layout.py` для строки 16 / столбцов
2/5/8/11 не находит ни одной пересекающейся пары (ни с ванильными
технологиями, ни с заголовками секций).

## Итерация 23: советники получили бонусы, конница — донских казаков и ванильную иконку

Три претензии пользователя к игре, каждая разобрана до причины и закрыта

### 1. «У Щуся и Григорьева нет бонусов»

**Причина.** Advisor-модификаторы даёт не блок `advisor = {}` в
`common/characters/`, а **идея**, объявленная в `common/ideas/` в категории,
имя которой равно слоту (`army_chief`, `high_command`, …): персонаж только
ссылается на неё через `idea_token`. В моде не было **ни одной** advisor-идеи —
все 18 советников нанимались пустыми. Второй дефект поверх: имена черт
`army_cavalry_speed_2` и `army_morale_2` выдуманы (таких черт в игре нет), а
ручной словарь `VANILLA_TRAITS` в аудите содержал те же фантомы — проверка
пропускала их, потому что сравнивала список с самой собой.

**Что сделано.**

1. `common/ideas/GLP_advisors.txt` — 18 advisor-идей в шести категориях
   (`army_chief`, `navy_chief`, `air_chief`, `high_command`,
   `political_advisor`, + `available` с гейтом на фокус для трёх военных
   миссий); модификаторы берутся из черт мода/ванили, у Щуся добавлен
   `modifier = { cavalry_speed_factor = 0.08 }` (его черта «рейдер Степи»).
2. `common/characters/GLP_characters.txt` — фантомные имена черт заменены
   существующими (`army_cavalry_2`, `army_regrouping_2`), абзац шапки
   переписан под инвариант «кадры + идея».
3. `localisation/{english,russian}/GLP_characters_l_*.yml` — 18 ключей
   `<token>_advisor_desc` (иначе в окне ставки описание советника пустое);
   паритет EN/RU соблюдён, BOM сохранён.
4. `events/GLP_diplomacy.txt` — «Кризис Григорьева» при отставке теперь зовёт
   `deactivate_advisor = GLP_ataman_grigoriev_advisor` перед `remove_ideas`
   (без этого idea-модификаторы остаются висеть на стране).
5. `common/national_focus/GLP_focus.txt` — вербовка `GLP_soviet_military_mission`,
   `GLP_german_military_mission`, `GLP_british_naval_drill` в награды фокусов
   (724/760/796): их advisor-блоки стояли в `visible`-гейте, но сам кадр не
   появлялся.
6. `tools/idea_pictures.tsv` — 18 строк «идея → picture» (реестр картинок
   сверяется `check_idea_pictures`).
7. Попутно найден дефект самого текста локализации: в двух новых `*_desc`
   кавычки стояли **внутри** значения (`… staff trait "Cavalry II"."`) —
   движок обрывает такую строку и показывает `???????`. Значения выровнены, а
   в `load_loc()` добавлена инвариантная проверка баланса кавычек (раздел 2).
8. `tools/vanilla_trait_names.txt` — снимок 999 имён ванильных черт из
   `localisation/english/traits_l_english.yml` базовой игры (зеркало
   `cbrzeczysz/hoi4-history` @ 1.14.1). Аудит больше не содержит
   рукописного списка имён: словарь грузится из файла и дополняется
   развёрнутыми семействами ставки (`army|navy|air_<семейство>_<1..3>` —
   54/48/42 имени, количества сверены со снимком).

**Новая проверка — раздел 17, `check_advisor_ideas()`.** Для каждого
`advisor = {}`: слот ∈ шести законных advisor-слотов; `idea_token` обязан
разрешаться в идею; категория идеи == слот; у идеи есть `allowed`; идея даёт
`traits` или `modifier`; все имена черт (и у кандидата, и у идеи) разрешаются;
черты кандидата обязаны быть подмножеством черт идеи; `picture` ∈ ванильные
`GFX_idea_generic_*` или спрайт мода; `has_completed_focus` в `available`
ссылается на существующий фокус; `high_command` без `ledger` — предупреждение.
Отдельно предупреждает о advisor-идеях, к которым нет персонажа.

### 2. «У кавалерийских дивизий должны быть модели Донских казаков»

`gfx/models/units/NTC_cavalry.*` (повстанческий всадник в чёрной папахе)
заменён на **`DON_cavalry.*`** — модель донского казака из того же
пакета Rise of Russia; `file =` у `GLP_cavalry_mesh` и `GLP_cavalry_2_mesh`
в `gfx/entities/GLP_units.gfx` переведён на новый меш (обе сущности,
`.mesh` + 3 `.dds`). Проверка совместимости: RoR использует тот же меш DON с
теми же пятью сабельными анимациями, которые уже подключены в
`GLP_cavalry_animations.asset`/`.anim` — скелет общий, поэтому файлы анимаций
не тронуты. Пять .anim и меш сверены побайтово с оригиналом репозитория.

`check_unit_models` усилена: требует `DON_cavalry.mesh` именно в обеих
кавалерийских `pdxmesh`, а для каждого меша читает из бинарника имена
встроенных текстур и проверяет, что файлы лежат рядом (иначе движок рисует
белую болванку — так раньше и ломался `NTC_cavalry_diffuse_.dds` с подчёркиванием).
Комментарий «В моде нет кастомных 3D-моделей» в `tools/glp_audit.py` был
ложью с итерации 4 — переписан.

### 3. «На карте у кавалерийских дивизий — иконки кавалерийских дивизий из ванильной игры»

Свою плитку-тачанку (итерация 22, пункт 1) мод **отдал ванильной графике**:

Объявление (texturefile + `noOfFrames = 2`, атлас из двух кадров) скопировано
из ванильного `interface/subuniticons.gfx`, где те же файлы использует
`GFX_unit_cavalry_icon_medium` / `_medium_white`. `GLP_tachanka.dds` (обе
плитки) и мастера `_src_div_cavalry*.png` удалены, `tools/build_division_icons.sh`
больше не собирает 92 — и собирает только знамёна 90/91, своего силуэта
рода войск в моде теперь нет вовсе.

Пины: `template_counter = 92` дописан конным добровольческим шаблонам
(«Казачья добровольческая конная дивизия» 90 → 92, «Испанская ударная конная
колонна» 91 → 92), «Ударный тачаночный курень» и «Трофейный отряд РПА»
остались на 92. Знамёна 90/91 теперь только у пехотных добровольцев
(«Офицерская добровольческая», «Интернациональная бригада CNT-FAI») — знамя
утверждает принадлежность, а не род войск, и конное название с знаменем
означало бы «на карте не конь».

`check_division_icons` переписан под это правило: спрайт counter'а с
`depicts != flag` обязан смотреть в `gfx/interface/counters/divisions_{large,small}/
[onmap_]unit_<род>_icon.dds`, путь обязан быть перечислен в `VANILLA_TEXTURES`
(список «живёт в базовой игре»), `onmap_`-вариант обязан соответствовать
мелкой фишке, имя силуэта — совпадать с `depicts`, `noOfFrames` — быть 2;
свой DDS рода войск — ошибка. `depicts = flag` по-прежнему проверяется на
76×42 / 30×12 и ARGB8888/DXT5.

## Итерация 22: иконки шаблонов дивизий по названию (конница = конь, а не танк)

Симптом в игре: у кавалерийских дивизий в дизайнере и на карте показывался
силуэт **танка**. Причина — не в ассетах, а в том, как HOI4 выбирает иконку
шаблона: без `template_counter` движок берёт силуэт под-юнита с наибольшим
`priority` среди линейных батальонов. У конного «Ударного тачаночного куреня»
(4 × `cavalry` + 2 × `motorized` + 1 × `light_armor` — бронеавтомобиль по ТЗ)
выигрывает танковый батальон: `light_armor` = 2501 против `cavalry` = 599.

### Что сделано

1. **Плитка конницы** — `template_counter = 92` → `GFX_div_templ_92_large`
   (76×42, дизайнер дивизий) и `GFX_div_templ_92_small` (30×12, фишка на карте):
   всадник с шашкой и тачанка, ванильный стиль (плоский силуэт `#517151`,
   верхняя световая растяжка, тёмная обводка; несжатый ARGB8888 DDS). Собирается
   `tools/build_division_icons.sh` из мастеров `tools/_icons_src/_src_div_cavalry*.png`;
   идемпотентно. На 30×12 обводка и растяжка отключаются — иначе силуэт
   превращается в нечитаемое пятно (покрытие 37,6 % → 16 %).
2. **Составы не менялись** — геймплей и снаряжение те же; род войск закрепляется
   явным counter (тот же механизм, что уже применён для добровольческих знамён 90/91).
3. **Исправлены оба расхождения**: «Ударный тачаночный курень им. Батьки Махно»
   (был танк → конь) и «Трофейный отряд РПА» из `on_actions` (конная группа имён,
   но иконка пехоты: `infantry` 600 > `cavalry` 599 → тоже конь).
4. **Реестр** `tools/division_icons.tsv`: `counter → плитки → что рисует`
   (90/91 — `flag`: знамя добровольцев род войск не утверждает, проверка к нему
   не применяется; 92 — `cavalry`).
5. **Новая проверка аудита `check_division_icons`**: для каждого шаблона дивизий,
   определённого модом (OOB 1936, `GLP_old_enemies`, `on_actions`, события, фокусы),
   пересчитывает иконку так же, как движок (ванильная таблица `priority` + свои
   `sub_units` из `common/units/*.txt`, колонки `combat_support` исключаются),
   и сверяет с родом войск из названия шаблона и его `division_names_group`;
   дополнительно требует, чтобы counter был в реестре, спрайты — определены,
   плитки — ровно 76×42 / 30×12 и ARGB8888/DXT5, а каждое имя в группе имён —
   упоминать род своей группы. Полная таблица соответствия 15 шаблонов —
   в `ICONS_REPORT.md`.

### Негативные тесты (4/4)

| Поломка | Результат |

| У конного шаблона убран `template_counter = 92` | «иконка не по названию: движок возьмёт силуэт «light_armor» (priority 2501 → tank), а ожидается horse … нужен template_counter» |

### Попутно

* «7-я Крымская бригада матросов и повстанцев» в **стрелковой** группе имён —
  новая проверка названий внутри `GLP_INF_HISTORICAL` → переименована в
  «7-я Крымская **стрелковая** бригада матросов и повстанцев».

### Остаточные ограничения (честно)

* Номера 90/91/92 лежат за диапазоном ванильных `GFX_div_templ_0…89`
  (дамп 1.14.1; 44…64 заняты DLC-файлами). Если Paradox расширит ванильный
  диапазон выше 89, новый counter надо сдвинуть — реестр в `tsv` и спрайты
  в `interface/GLP_division_templates.gfx` правятся в одном месте, проверка
  аудита это учтёт.
* В-игровой визуальный контроль не выполнялся (нет запуска HOI4): проверка
  статическая и повторяет алгоритм движка по ванильным `priority`.
* Прибитый counter — это именно **выбор автора**, а не живой пересчёт состава:
  если игрок переделает «Тачаночный курень» в чистый танковый кулак, иконка
  останется конной, пока он сам не нажмёт «DEFAULT_DIV_TEMPL_SYMBOL» в окне
  выбора символа дивизии. Обратная сторона — конная дивизия с ротой
  бронеавтомобилей больше не «предается» танком.
* Добровольческие шаблоны (90/91) сознательно показывают знамёна, а не
  родовую иконку: `depicts = flag` в реестре — и проверка соответствия
  «название ↔ иконка» к ним не применяется. Если нужны кони и там, counter
  92 достаточно дописать в эти два шаблона (они locked, состав не пострадает).

## Итерация 21: фикс окон событий (??????? + чёрный шрифт) и новые обои меню

Симптомы в игре: заголовки/описания событий — знаки `???????`, текст в окне
чёрный там, где должен быть белым. Две независимые причины, обе исправлены:

1. **Локализация Испанского сценария без номера версии.** Все 62 строки
   `GLP_spain_scenario_l_{russian,english}.yml` имели вид `key: "..."`
   вместо обязательного `key:0 "..."` — HOI4 такие строки молча не грузит,
   движок показывает сырой ключ как `??????` (18 событий цепочки
   `glp_spain2.*`: заголовки, описания, все опции). Исправлено добавлением
   `:0`; аудит усилён проверкой `LOC_NOVER` — строка `key: "..."` теперь
   ошибка сборки, а не молчаливый пропуск.
2. **`interface/eventwindow.gui` был копией старой ванили с чужими шрифтами.**

  готовых эмблем способно дать полосатость, которую в этой среде нечем
  проконтролировать визуально.
* **Проверки, требующие движка, не выполнялись**: рендер окна событий,
  перенос/обрезка текста, фактическая читаемость шрифтов, поведение
  `mean_time_to_happen`, корректность загрузки сценария. Здесь доступна
  только статическая проверка файлов.

## Итерация 6: краш после замены моделей конницы — найден и устранён

Симптом: краш игры появился после добавления моделей войск (итерация 4).

### Методика

Все 25 импортированных бинарников (`gfx/models/units/*`) сверены **побайтово**
(git blob SHA-1) с оригиналами в GitHub-репозитории Rise of Russia
(`Gtym33/Kursach-Himiya`) — все 25 файлов идентичны оригиналу, коррупции нет.
Скелеты мешей и `.anim` сопоставлены по костям (31 кость, полное совпадение).
Скриптовые определения сверены с оригинальными `YR_cavalry.gfx`,
`YR_units_cavalry.asset`, `_npt_animation_units.asset` RSR и с дампом
базовой игры (`units_cavalry.asset`/`infantry.gfx`/`units_infantry.asset`).

### Найденные ошибки

1. **Краш (основной): кавалерийские сущности собирались через `clone`.**
   `GLP_cavalry_entity` и `GLP_cavalry_2_entity` использовали
   `clone = "cavalry_entity"`, а `GLP_infantry_mg_rider_entity` —
   `clone = "generic_infantry_mg_rider_entity"`. Это единственное
   структурное отклонение от проверенного паттерна RSR (исходника моделей):
   RSR определяет все «верхние» кавалерийские сущности **явно**
   (`pdxmesh = infantry_cavalry_horse_frame_mesh` + 7 стейтов + 3 attach:
   infantry/cavalry/horse + scale). Кросс-файловый clone к ванильным
   cavalry-сущностям — недостоверный путь (дамп базовой игры и опыт 1956:
   «a parent must be in the same file as its clones to avoid errors in log»).
   **Исправлено:** все три сущности переписаны явными определениями
   (паттерн RSR/базовой игры), без единого `clone` к cavalry-сущностям.
2. **`GLP_cavalry_2_entity` клонировал НЕПРАВИЛЬНОГО родителя** —
   `cavalry_entity` (винтовочная конница), а не `cavalry_2_entity`; у него
   нет `propagate_state = { cavalry = "idle" }` для MG-всадника.
   **Исправлено** явным определением по образцу ванильного `cavalry_2_entity`.
3. **Трофейная механика не работала:** `check_variable = { random < 0.65 }` —
   `random` не является переменной (`check_variable` оперирует только
   `set_variable`); триггер всегда падал. **Исправлено:** штатный триггер
   вероятности `random = 65 / 45 / 15` (проверено по wiki Triggers: `random` —
   отдельный процентный триггер; `create_unit = { division = "..." }` и
   `teleport_armies = { limit to_state_array }` при этом подтверждены
   ДОКУМЕНТИРОВАННЫМ синтаксисом и оставлены без изменений).
4. **Не задокументированное требование La Résistance:**
   `ideology = anarchism` у Махно — ванильная идеология только при наличии
   DLC (1.9, 2020). Без DLC загрузка сценария роняет ошибку на персонаже.
   **Исправлено:** требование добавлено в README (раздел «Требования»).

### Что проверено и признано корректным (было под подозрением)

- Флаги: 82×52 / 41×26 / 10×7, 32 bpp, без сжатия — эталонный размер HOI4.
- `cavalry_entity`/`generic_infantry_mg_rider_entity`/`cavalry_2_entity`
  действительно существуют в базовой игре (дамп `units_cavalry.asset`:
  «moved from units_cavalry.asset»; под-юнит `cavalry` → `sprite = cavalry`).
- Лошадь `infantry_cavalry_horse_mesh` объявляет `cavalry_attack`/
  `cavalry_attack_2` — стейты combined-сущностей валидны; `Saddle_Node` есть.
- GER-оружие (`GER_infantry_weapon_*_entity`) — ванильные сущности, все
  ноды (`Right_Hand_node`, `Left_Hand_node`, `mid_back_node`, `Root_node_2`)
  присутствуют в импортированных мещах.
- `CHI_sword_sabre_*.dds` (ножны) — побайтовые алиасы, Waking the Tiger не
  требуется; `.anim`-файлы завершаются корректно, костный скелет совпадает.
- Решения: группа решения и есть категория (современный формат 1.16+),
  все 4 категории GLP объявлены — ошибок нет.
- `music.asset` не «перекрывает» ваниль (сливается), но ванильный
  `maintheme` переопределён — поведения краш-уровня нет.

## Итерация 6: заставка показывает кинематографический текст; «?????» и технические имена устранены

### Симптомы

1. В окне заставки не было кинематографического текста (лента титров не показывалась вовсе).
2. На кнопке переключения режимов красовалось техническое имя `GULYAIPOLE_TOGGLE_MODE_DYNAMIC`.
3. В цитатах загрузки, газете `glp_news.100`, фокусах, духах и названии мода вместо букв — «?????????????».

### Причины и исправления

1. **Маска ленты титров была чёрной.** Движок Clausewitz маскирует `scrolling`-анимацию по яркости **RGB**-каналов маски; альфу маски он не читает. В сборке маска `gulyaipole_text_mask.dds` хранила градиент затухания только в альфе при нулевом RGB — титры умножались на ноль и были невидимы. Маска перегенерирована белым градиентом в RGB (непрозрачная альфа).
2. **Лента была заполнена наполовину.** Текст в `gulyaipole_text_crawl.dds` (310×4096) начинался с y≈1900 — почти половину цикла прокрутки окно стояло пустым. Лента перегенерирована генератором `tools/render_intro_crawl.py`: текст берётся прямо из ключа `GULYAIPOLE_EPIC_INTRO_TEXT` (RU), заполняет 96% высоты (y=64..4036), `animationlooping = yes` — повторное открытие заставки всегда показывает движущийся текст.
3. **Техническое имя на кнопке.** `buttonText` ссылался на `defined_text` `GULYAIPOLE_TOGGLE_MODE_DYNAMIC`, у которого нет записи в `.yml` — движок печатает на кнопке имя ключа как есть. Defined_text удалён; вместо одной кнопки — две наложенные с обычными ключами `GULYAIPOLE_TOGGLE_TO_CRAWL` («Кино-заставка») и `GULYAIPOLE_TOGGLE_TO_TEXT` («Читать текст»), видимость переключают триггеры `*_visible` в scripted GUI.
4. **Режим по умолчанию — читаемый текст.** Локализованное поле `GULYAIPOLE_EPIC_INTRO_TEXT` рендерится штатным шрифтом игры и видно гарантированно; лента титров включается кнопкой (флаг `glp_intro_crawl_mode`). Кнопка старта сбрасывает режимные флаги — повторный показ снова открывается на читаемом тексте.
5. **«?????????????» — дореформенная орфография вне атласа шрифтов.** В русской локализации было **1455** букв `ѣ`/`і` (особенно в `loading_tips`: 685×2 файла), которых нет в bitmap-атласе HOI4 — движок рисует вместо них «?». Все заменены на современные `е`/`и` (твёрдый знак `ъ` в атласе есть и сохранён ради колорита цитат). Имя мода в `descriptor.mod` приведено к тому же алфавиту.
6. **Карта заставки.** Сепийная карта Екатеринославщины содержала AI-надписи, читающиеся как бессмыслица; арт отредактирован с удалением всех надписей и пересобран в 320×260 DXT1.

### Новые проверки аудита (защита от регресса)

- `check_loc_font_charset()` — запрещает в значениях локализации символы вне атласа HOI4 (`ѣ і ї є ґ ѳ ѵ` и т.п.).
- `check_intro_gui_keys()` — каждый `text=`/`buttonText=` ключ окна заставки обязан существовать в RU и EN локализации; direct-использование `defined_text` без записи в `.yml` запрещено.
- `check_intro_crawl_textures()` — размеры ленты/маски, яркость маски по RGB (>0.5), наличие текста в верхней и нижней четвертях ленты, воспроизводимость (генератор и `*_v3.png` источники на месте).

Аудит: **0 ошибок** (предупреждение об одинаковых OGG-заглушках Монгол Шуудан — известное, ждёт настоящих дорожек).

### Новые инварианты аудита — `check_crisis_events()`

В `tools/glp_audit.py` добавлена функция `check_crisis_events()` (вызывается в `main()`) с тремя инвариантами. Каждый инвариант проверен негативным тестом, который инжектирует ломающую правку и убеждается, что аудит её ловит (после чего правка откатывается).

**Инвариант 1 — каждое `glp_crisis.*` запускается.**
Считаем вхождения `id = X` в `common/national_focus/`, `common/on_actions/`, `common/decisions/`, `events/`. В `common/*` объявлений быть не может, поэтому каждое упоминание = вызов. В `events/` одно вхождение = только объявление; > 1 — есть вызов. Каждый id должен быть «referenced» хотя бы одним файлом.

*Негативный тест*: добавляем `country_event = { id = glp_crisis.99 ... }` с локализацией. Аудит печатает `crisis: событие glp_crisis.99 не запускается ни из on_actions, ни из фокусов, ни из других событий — мёртвый груз`. После восстановления — 0 ошибок.

*Промежуточный фикс*: первая версия использовала regex `(?:country_event|news_event)\s*=\s*\{[^}]*?id\s*=\s*(glp_crisis\.\d+)`, который ловил **объявление** события (потому что `id` идёт первым аргументом блока) наравне с **вызовом**. Заменено на счётчик вхождений `id = X` в файле: 1 = только объявление, > 1 = есть вызов. В `common/*` всегда вызов.

**Инвариант 2 — `retire`/`retire_character` под guard `has_character`.**
Ищем обе формы: `GLP_X = { retire = yes }` и `retire_character = GLP_X`. Проверяем, что в 200 символах контекста до `retire` есть `has_character = GLP_X`. Без guard'а движок 1.19.2 роняет silent error, если персонаж погиб ранее (что вполне реально для Григорьева, Махно, Скоблина в зоне боевых действий).

*Негативный тест*: снимаем `if = { limit = { has_character = GLP_ataman_grigoriev } }` вокруг `GLP_ataman_grigoriev = { retire = yes }` в `glp_crisis.10.c`. Аудит печатает `events/GLP_diplomacy.txt: 'GLP_ataman_grigoriev = { retire = yes }' без if = { limit = { has_character = GLP_ataman_grigoriev } } guard'а -- 1.19 роняет silent error, если персонаж погиб ранее`. После восстановления — 0 ошибок.

**Инвариант 3 — флаги ступеней 40/41/42 очищаются.**
В финальной опции ступени 3 (`glp_crisis.42`) с `trigger = { has_country_flag = GLP_white_step_3_* }` обязан быть `clr_country_flag` того же флага И парного ступени-2 (`GLP_white_step_2_sidelined` для ветки dispersed, `GLP_white_step_2_favored` для parallel). Иначе повторный запуск цепочки даст «branch already chosen» и опция перестанет срабатывать.

*Негативный тест*: удаляем `clr_country_flag = GLP_white_step_2_sidelined` из опции `.a` ступени 3. Аудит печатает `events/GLP_diplomacy.txt: glp_crisis.42 — финал ветки 'dispersed' не очищает GLP_white_step_2_sidelined`. После восстановления — 0 ошибок.

*Промежуточный фикс*: первая версия искала `id = glp_crisis.42` через жадный regex `id\s*=\s*glp_crisis\.42[^{]*\{` — он матчил **вызов** `country_event = { id = glp_crisis.42 days = 120 random_days = 30 }` в `glp_crisis.41` (нет `{`), и далее `body.find('{', m.start())` находил `{` от **объявления** ниже по тексту — но регулярно давал ложные срабатывания и пустой `body42`. Заменено на строгий `country_event\s*=\s*\{\s*\n\s*id\s*=\s*glp_crisis\.42`, после чего `body42` корректно ограничен сбалансированным brace-обходом.
